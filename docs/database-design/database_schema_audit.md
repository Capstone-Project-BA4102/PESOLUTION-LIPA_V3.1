# PESOLUTION Database Schema Audit

## Audit Scope and Evidence

This audit compares the live Supabase `public` schema retrieved read-only on October 15, 2026 with Table 3-6, “Major database tables of PESOLUTION,” in `PESOLUTION_REVISED.docx`. The live source was Supabase PostgREST OpenAPI metadata generated by the deployed database. Repository SQL and application queries were used as supporting evidence, not as substitutes for the live table/column inventory. No records, migrations, or database objects were changed.

## Executive Findings

- Live public tables: **26**.
- Live public foreign-key relationships surfaced: **29**.
- Tables listed in manuscript Table 3-6: **14**.
- Table 3-6 entries absent from the live public schema: **0**.
- Live tables omitted from Table 3-6: **12**.
- Conclusion: Table 3-6 accurately identifies the principal operational entities it names, but it is not a complete inventory of the current live database.

## Integrity and Cardinality Limitations

- The live OpenAPI schema identifies PKs, FKs, nullability, types, and defaults. It does not provide a complete catalog of unique constraints or indexes.
- The ERD uses conservative parent-to-child cardinality from FK nullability. One-to-one claims such as `applications` to `referrals` require direct catalog verification of uniqueness before being stated as live facts.
- Supabase `auth.users`, `storage.buckets`, and `storage.objects` are managed outside the exposed `public` schema and are not represented as ordinary live public tables in this ERD.
- The repository migration files declare several cross-schema links to `auth.users`; these are supporting evidence only and are not presented as live-verified public-schema FKs.

## Recommended Manuscript Wording

“The deployed PESOLUTION database contains 26 tables in its exposed public schema. Table 3-6 presents the principal operational tables, while supporting tables maintain account-email audits, public-site content, service monitoring, and research evaluation data. Relationships shown in the ERD represent foreign keys verified from the live Supabase schema metadata; cross-schema authentication relationships are documented separately where direct catalog verification is unavailable.”
